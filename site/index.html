Side by side

Two designs

Vercel's World and this World implement the same SDK interface.

The path of start()

  1. getDeploymentId() from the environment; "latest" asks the Vercel API
  2. Cross-deployment only: a health probe through the queue and a stream
  3. createRunId: a ULID tagged with one of 23 regions
  4. Per-run AES key: derived in the function, or fetched from the Vercel API
  5. In parallel: POST run_created to the backend as one frame, and send the start to the queue topic with its deployment ID
  6. The queue triggers the function; run_started answers with the whole log as a frame stream

The path of start()

  1. The World client mints the run ID; its time picks the epoch, its hash the store shard
  2. In parallel: the store shard writes run_created in one SQLite transaction, and hands the start to a queue shard
  3. 202 back to the caller after both
  4. The queue shard calls the run's runner through a stub its alarm made; the runner calls the executor of the run's deployment
  5. Replay; a turn's step_created events go 500 per call, and steps hash over queue shards to step runners
  6. Stores push list rows to index shards; hook rows before the write answers

Life of a run

Where workflow code runs

Two engines

Workflow code runs in a VM so every replay makes the same decisions. Steps run outside it.

QuickJS restores a snapshot, then reads the tail. The node engine reads everything.

Scaling out

Scaling out

Nothing on the hot path is shared by every request.

Add capacity by appending an epoch. Runs never move.

A run's steps all land on its store. Batching its writes, 500 per call, keeps that store under 128 MB.

A chain of calls has a depth budget: 14 from a request, 16 from an alarm. Stubs first called from an alarm keep the fresh budget.

LOCATION_HINT puts every object in one region. A run's store creates its runner, so they sit together: about 70 ms per step together, 105 to 140 ms apart.

Why

Decisions

Open one for the reasoning.

Be an SDK World, not a port to Cloudflare WorkflowsRuns on the published workflow 5.5.0, unpatched.

The SDK owns replay, steps, hooks and retries. The World only has to store events and deliver messages, so workflow code and its semantics stay exactly the SDK's.

Hash runs over store shards, not one object per runFirst call to a new object: about 1.7 s.

A run's whole log must be ordered, so it lives in one Durable Object. A new named object was slow on its first call, so runs share warm shards instead of each creating its own.

Add capacity with epochs, never by reshardingToo many shards is slower too: cold objects.

A run's ULID time picks its epoch, and each epoch has its own shard counts. New runs land on the newest epoch; old runs never move, so no migration and no lock.

No global directoryCreation is two object calls, in parallel.

Nothing every request shares. Hook tokens live on token shards, list rows on index shards, and a run is found from its ID alone.

Replays one at a time per run; steps spread by keyNo duplicate step starts at 1,000 parallel steps.

A run's workflow messages go to its own queue shard and replay one at a time, with pure wakes coalesced. Steps hash by idempotency key over every shard.

Run flows on runners, off the queue shardsCreation was 3x faster with flows off the queue shards.

Queue shards only hold and hand off messages; runners make the flow requests. The queue keeps accepting work while flows run.

Index shards for listsBackfill of 2,689 existing stores took under 2 minutes.

Cross-run lists read index shards fed by an outbox on each store. Hook rows wait for their push, because the SDK reads a hook right after creating it; run rows do not hold POST /runs.

Put objects in one region, and runners next to their storesAbout 70 ms per step next to the store, 105 to 140 ms apart.

LOCATION_HINT creates every object in one region. A run's store creates its runner without the hint, so the runner lands next to it; workflow code calls its store a few times per step.

Batch a turn's fan-out per flow requestStore memory at 5,000 steps: 1.4 GiB to 59 MiB.

A replay that starts thousands of steps sends their events and publishes in batches of 500, two calls in flight, keyed to its own request. Nothing is shared across requests.

Reset the call chain from an alarmMeasured: 14 levels from a request, 16 from an alarm.

A queue shard calls its runners through stubs it first called from its own alarm, so every delivery starts a fresh chain of calls. A call that still runs out is retried as a 503.

Large data goes in byte streams1 GiB in 32 MiB chunks, every byte checked.

Values over 1 MiB go to R2. Streams move in chunks of up to 32 MiB with a writer lease, and a flow waits for its background writes, which the platform otherwise cancels 30 s after a request ends.
